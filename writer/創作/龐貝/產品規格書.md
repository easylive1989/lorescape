# 龐貝 VN 產品規格書（L0）

> **這是 [[視覺小說架構分析]] 的 L0 層產出**。L1 之後的所有工作以本文件為前提；本文件改動＝下游全部重估。
> **狀態**：2026-08-13 定案為**短篇形式 ＋ 背景與立繪**（同日稍早曾暫定 2–4 小時旗艦作，已撤銷）。數量估算均標註假設，**須以第一篇實測校正**。

---

## 1. 已鎖定的規格

| 欄位 | 決定 |
|---|---|
| **形式** | **短篇**——併入既有短篇主線，**不做 2–4 小時旗艦作** |
| **單篇時長** | 10–15 分鐘 |
| **平台與畫面** | **手機、直式（portrait）**——背景一律 9:16，下方約 35% 為對話框區（[[美術風格聖經]] §3.1） |
| **視覺規格** | **背景 ＋ 立繪** |
| **美術來源** | **AI 生成**（見 §5.5——成本從「每張圖的錢」轉移到「一致性與考據的工」） |
| **SKU 單位** | **景點包**（一個地點 × 一個時刻），非「時期」——見 §2.3 與 [[故事景點選點標準]] |
| **變現** | 沿用 [[互動歷史短篇App定價方案]]：免費入場 → 時代包 → 訂閱 |
| 分歧密度 | 珠鏈式：3–5 個選擇、1–2 個狀態變數、2–3 個結局（短篇尺度，見 §4） |
| 語音 | 無 |

### 1.1 ⚠️ 這個組合的成本問題（必須正面處理）

既有的定價與營收模型（[[互動歷史短篇App定價方案]]、[[營收天花板與地板估算報告]]）建立在「**純文字、可高頻上架**」之上。加上美術之後：

- 每篇多出背景與立繪的產出時間 → **上架節奏變慢**
- 訂閱制的前提是「內容持續變多」→ **節奏一慢，訂閱就撐不住**
- 免費入場的 8 篇 → **等於 8 篇的美術成本純支出**

**這個問題不會自己消失，但可以用資產結構解掉——見 §2。**

## 2. 核心設計：美術以「時代包」攤提，不以「篇」攤提

### 2.1 資產重用結構

**同一個時代包內的所有短篇共用同一套背景庫。** 龐貝的中庭、街道、廣場、熱食攤、浴場畫一次，之後每一篇龐貝短篇都在用它。

| | 第一篇 | 同時代第 2–8 篇 |
|---|---|---|
| 背景 | **建立整套城市場景庫 10–12 張** | 新增 0–2 張 |
| 立繪 | 3–4 角色 × 4 表情 | 新增 1–2 角色（部分角色跨篇復用） |
| UI／引擎／pipeline | 一次性建置 | 0 |
| **邊際成本** | **高** | **低** |

**結論：貴的是「開一個新時代」，不是「多寫一篇」。** 這正好對上既有的 SKU 結構——[[互動歷史短篇App定價方案]] 已經指出「七大時期研究報告 ＝ 七個現成的商品 SKU」，現在它同時也是**七個美術資產包**。

### 2.2 敘事上的必然結果：龐貝是一組群像短篇，不是一篇

10–15 分鐘塞不下「日常 → 徵兆 → 崩毀 → 餘生」的完整弧線，硬塞就是每一幕都太薄。但**一個時代包 6–8 篇**就放得下——而且是更好的形式：

> **每篇 ＝ 同一座城、同一場災難、不同人物的視角。**
> 銀行家、女祭司、被釋奴、奴隸、角鬥士、外地商人、孩子……
> 每篇獨立 10–15 分鐘可單獨讀完；全部讀完是一部完整的群像作品。

這個結構同時解決三件事：

1. **美術重用有敘事正當性**——不是為了省錢才重複場景，是同一座城本來就該重複出現。玩家在第 5 篇認出第 1 篇的街角，是效果不是破綻。
2. **災難的階級落差被呈現出來**——這是龐貝題材最強的東西（[[龐貝史實紅線]] §6），單一主角做不到。
3. **時代包成為真正的「作品」而非「合集」**——提高時代包 SKU 的售價正當性。

**跨篇的設計規則**：篇與篇之間可互相呼應（A 篇的路人是 B 篇的主角），但**每篇必須能獨立讀懂**，不能要求讀者按順序。

### 2.3 SKU 單位改為「景點」而非「時期」

[[互動歷史短篇App定價方案]] 原以「七大時期 ＝ 七個 SKU」切分，但**加入美術後這個切法會壞掉**：一個「時期」橫跨數十個地點與數百年，背景庫完全無法重用，等於每一篇都要重畫。

**背景庫綁定的是地點，不是年代。** 因此 SKU 單位改為：

> **一個景點包 ＝ 一個地點 × 一個時刻 × 6–8 篇群像短篇 ＝ 一套背景庫**

七大時期研究報告仍然是素材庫與考據基礎，但**商品的切分改以景點為單位**。景點的挑選標準與候選清單見 [[故事景點選點標準]]。

## 3. 單篇規模

**假設**：中文閱讀速度以 300 字／分鐘規劃；短篇分歧膨脹取 1.4×。兩者須以第一篇實測校正。

| 項目 | 數值 |
|---|---|
| 單次通關 | 10–15 分鐘 |
| 通關字數 | 3,000–4,500 字 |
| **總撰寫量** | **4,500–6,500 字／篇** |
| 場數 | 8–12 場（場均 400–700 字） |
| 選擇點 | 3–5 個 |
| 結局 | 2–3 個 |

**一個時代包（8 篇）＝ 總撰寫量約 40,000–52,000 字。** 與 2–4 小時旗艦作的 54–68k 字是同一個量級——差別在於**它可以分 8 次交付、每次都能上架、每次都能收到市場回饋**，而不是埋頭 7–10 個月才第一次見光。這是短篇形式真正的優勢，不只是省事。

## 4. 短篇尺度下的結構調整

[[視覺小說架構分析]] 的七層仍然適用，但 L3 的建議值隨規模改變：

| | 架構分析的原建議（2–4 小時） | **短篇（10–15 分鐘）** |
|---|---|---|
| 分歧拓撲 | 分岔再收束 | **珠鏈式**——分歧後很快收束 |
| 狀態變數 | 3–5 個 | **1–2 個** |
| 結局 | 4–8 個 | **2–3 個** |
| 幕結構 | 四幕（日常／徵兆／崩毀／餘生） | **單一情境 ＋ 一次轉折**；四幕結構改由**整個時代包**承載 |

**短篇最容易寫壞的地方**：想在 10 分鐘內同時做好人物建立與災難場面。**建議每篇只做一件事**——這一篇是關於這個人的一個選擇，火山是背景不是主角。

## 5. 資產規格

### 5.1 龐貝場景庫（一次性建置，10–12 張）

中庭（atrium）／列柱庭園／街道／廣場（62 年地震後的修復工地狀態）／熱食攤（thermopolium）／麵包坊／浴場／劇場／神廟／港口／城門與城外道路／山坡葡萄園

**變體規則**：時段與災難氛圍（晴日／黃昏／夜／灰雨／火光）**用引擎色調濾鏡 ＋ 落灰粒子做，不重繪**。只有畫面內容真的改變（屋頂坍塌、浮石堆積高度）才進重繪清單，這類**結構性變體 4–6 張**，且它們同時是災難高潮的畫面（見 §5.3）。

### 5.2 立繪

| | 數量 |
|---|---|
| 每篇主要角色 | 3–4 人 × 4 表情 |
| 主角 | **不做立繪**（第一人稱慣例，省一整套且強化代入） |
| 跨篇復用 | 群像結構下，配角會在別篇當主角——**立繪庫隨篇數累積而非線性增加** |
| 第一篇繪製量 | 基底 3–4 張 ＋ 表情差分約 12–16 張 |

### 5.3 高潮畫面（不新增資產類別）

不做事件 CG，改用 §5.1 的**結構性變體背景**充當：去掉立繪、關掉對話框、全螢幕演出同一場所的毀滅版本。噴發柱、屋頂坍塌、逃出城門三個瞬間至少各留一張——這是商店頁面與社群分享要用的圖。

### 5.4 音效與 UI（一次性）

BGM 5–6 首、音效 20–30 個、UI 一整套（含景點包／訂閱的購買與解鎖流程）。**音效優先於美術精細度**——災難敘事裡聲音就是時鐘。

### 5.5 AI 生成美術

**成本結構改變了，但沒有消失——它移動了位置。**

| | 委外／自繪 | **AI 生成** |
|---|---|---|
| 每張圖的錢 | 高 | 趨近零 |
| 真正的成本 | 金錢與排程 | **一致性的工 ＋ 考據審查的工** |
| 瓶頸 | 畫師產能 | **同一個角色在不同場景長得一樣、同一個場所在不同時段是同一個地方** |

#### 必要的工作流

1. **風格聖經**：固定的 prompt 骨幹（畫風、視角、光線、色調、線條）＋ 一組定版參考圖。全案共用，新圖一律從它長出來，不要每次重新想 prompt。
2. **角色參考表**：每個角色定版一張基底，**表情差分用局部重繪（inpainting）而非整張重生**——整張重生幾乎必然跑掉五官與服裝細節。
3. **場景定版**：每個場所定版一張，時段與災難變體**由引擎濾鏡處理**（§5.1 已定的規則，在 AI 流程下更重要——重生一次就是換一個地方）。
4. **統一後製**：全部產出跑同一組色調與邊緣處理，蓋掉來源差異。

#### ⚠️ 最大的風險：AI 美術與「史實不杜撰」直接衝突

**AI 會生成看起來合理但史實錯誤的畫面**——把羅馬街道畫成中世紀、服裝混搭不同世紀、建築細節套用錯的文明、在龐貝畫出不存在的東西。這與本專案的核心原則（[[龐貝史實紅線]]）正面衝突，而且**錯誤在畫面上比在文字裡更難被自己發現**。

**對策：把 [[龐貝史實紅線]] §4 的時代錯置清單轉成一份美術驗收清單**，每張定版圖逐條過。這是本規格下不可省略的一道工，也是文字考據做得再好都補不回來的破口——玩家會先看到圖。

#### 兩個商業面注意事項

- **平台揭露規定**：Steam 要求揭露 AI 生成內容；行動平台的規定須另行查證（本文件不臆測現行條文，上架前實查）。
- **受眾觀感**：獨立敘事作品的受眾對 AI 美術有一部分負面反應。**行銷主打文本與考據，把美術定位為氛圍層而非賣點**——這與本專案的實際優勢也相符。

## 6. 對既有定價方案的三處修正建議

規格改變後，[[互動歷史短篇App定價方案]] 有三處需要重估：

| # | 原方案 | 建議修正 | 理由 |
|---|---|---|---|
| 1 | 免費 8 篇 | **免費篇集中在同一個景點包內**（例：龐貝的前 2–3 篇） | 共用同一套背景庫，獲客成本只有一套美術；散在 8 個時代等於免費送 8 套美術 |
| 2 | 訂閱 NT$ 90／月 | **上架節奏須先用實測驗證**（見 §7），撐不住就退為景點包買斷制 | 訂閱的前提是內容持續變多，加了美術之後這條前提要重新驗證 |
| 3 | 時代包 NT$ 150 | **改為景點包，且可上調**——有美術，且是群像結構的完整作品而非合集 | §2.2 的結構提高了售價正當性 |
| 4 | SKU ＝ 七大時期 | **SKU ＝ 景點**（見 §2.3） | 背景庫綁定地點而非年代，以時期切分等於放棄美術重用 |

**[[營收天花板與地板估算報告]] 的模型需要同步重跑**：成本端多了美術（每個景點包一次，AI 生成下主要是工時而非金錢），營收端的包售價、SKU 數量與上架節奏都變了。這件事應在第一篇實測完成後做，屆時才有真實數字可代入。

## 7. 里程碑

| 階段 | 內容 | 估時 |
|---|---|---|
| **前期** | L1 命題 → L2 Bible → 群像人物盤點（決定 8 篇各是誰） → 第一篇場景清單 | 2–3 週 |
| **第一篇（垂直切片）** | 含龐貝場景庫、UI、引擎、pipeline 全套一次性建置 | 6–10 週 |
| ⬆️ | **在此校正一切**——最關鍵的實測數字是「**第二篇要花多久**」 | |
| **第 2–8 篇** | 每篇寫作 ＋ 少量新增美術 ＋ 組裝 | 估 2–4 週／篇 |
| **景點包完成** | | 約 8–14 個月 |

> **第二篇的實測工時是整個商業模型的關鍵變數。** 它決定上架節奏，上架節奏決定訂閱制成不成立，訂閱制決定 [[營收天花板與地板估算報告]] 的哪一種情境適用。**做完第一篇不要急著做第三篇，先把第二篇的工時量出來。**
