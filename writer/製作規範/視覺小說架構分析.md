# 視覺小說架構分析

> **用途**：釐清「做一部視覺小說（VN）需要先備齊哪些東西」，以及各層之間的依賴順序。
> **適用對象**：龐貝主題 VN（人物可杜撰、史實不可杜撰）。史實邊界另見 [[龐貝史實紅線]]。
> **狀態**：架構分析。**L0 已於 2026-08-13 鎖定核心三項，規格見 [[產品規格書]]**；文末「待決事項」為尚未回答的部分。

---

## 0. 結論先講

**視覺小說的架構是七層，而且必須由上而下鎖定——上一層沒鎖，下一層寫的東西大概率要重做。**

| 層 | 名稱 | 產出物 | 沒鎖就往下做的後果 |
|---|---|---|---|
| **L0** | 產品規格 | 一頁規格書 | 寫了 8 萬字才發現只賣得動 1 萬字的形式 |
| **L1** | 命題 | Logline ＋ 能動性契約 | 分歧寫完了但每條讀起來都一樣 |
| **L2** | 世界 | Setting Bible ＋ 史實紅線 | 第 12 場才發現主角的階級做不出那個行為 |
| **L3** | 結構 | 分歧拓撲 ＋ 結局矩陣 ＋ 旗標表 | 分歧爆炸，寫不完也測不完 |
| **L4** | 場面 | 場景清單 ＋ 角色卡 ＋ 劇本 | 美術需求無法估算，成本失控 |
| **L5** | 呈現 | 資產清單 ＋ 引擎專案 | 美術做完才發現用不上／不夠用 |
| **L6** | 生產 | Pipeline ＋ QA ＋ 里程碑 | 做到 70% 卡死，永遠上不了架 |

**對一人團隊而言，最關鍵的三個決定分別在 L0（規模）、L3（分歧拓撲）、L5（美術來源）**——這三個決定佔了總成本變異的絕大部分，其餘都是執行。

**本專案的特殊約束**：這是**已知結局**的歷史題材（城市會毀滅），所以張力不能建立在「會不會發生」，只能建立在「誰活下來、付出什麼代價、你成為什麼樣的人」。這個約束會一路貫穿 L1 到 L4，不是文學風格問題，是結構問題。

## L0 產品規格——先鎖這個，其餘才有意義

動筆前必須有數字的六個欄位：

| 欄位 | 選項光譜 | 影響到什麼 |
|---|---|---|
| **單篇時長** | 10 分鐘 ／ 30–60 分鐘 ／ 3–8 小時 | 字數、資產量、售價、上架節奏 |
| **分歧密度** | 動態小說（零分歧） ／ 有限分歧 ／ 全分歧樹 | 寫作量的乘數（見 L3） |
| **視覺規格** | 純文字 ／ 背景＋文字 ／ 背景＋立繪 ／ 加 CG 事件圖 | **成本結構的最大分水嶺** |
| **語音** | 無 ／ 部分 ／ 全語音 | 有語音就無法輕易改稿，等於鎖死劇本 |
| **平台／引擎** | Web ／ iOS App ／ Steam；Ren'Py ／ ink ／ Twine ／ ChoiceScript ／ 自製 | 決定發佈通路與變現形式 |
| **語言** | 繁中 only ／ 繁中＋英 | 英文版是把總成本再乘一次的決定 |

### ⚠️ 與既有產品決策的張力（必須先解決）

[[互動歷史短篇App定價方案]] 鎖定的規格是「**Choice of Games 形式的分歧敘事 ＋ 單篇約 10 分鐘 ＋ 純文字**」；[[營收天花板與地板估算報告]] 的營收模型、[[台灣數位內容付費趨勢分析]] 的四層定價，全部建立在那個規格上。

「**視覺小說**」比那個規格多了一整層美術，這是兩件不同的產品：

| | 既有規格（純文字分歧短篇） | 視覺小說 |
|---|---|---|
| 每篇成本 | 只有寫作時間 | 寫作 ＋ 背景 ＋ 立繪 ＋ 事件圖 ＋ 組裝 |
| 產出節奏 | 可高頻上架（訂閱制成立的前提） | 慢，難以支撐「定期上架」 |
| 訂閱制 | 成立（內容庫可持續加深） | 難成立，偏向買斷制單一作品 |
| 對照原型 | ChoiceScript 作品 | LINE WEBTOON／商業 VN |

**注意這正是 [[台灣數位內容付費趨勢分析]] 已標記過的變數**：LINE WEBTOON 是既有產品的形式原型，而「有圖 vs 純文字」是唯一但重大的差異。做 VN＝主動選擇了「有圖」那一側，等於推翻既有定價與營收模型的一個前提。

**三條路**：

1. **VN 是主線**——單一買斷的長作品，重新做定價，訂閱制作廢。
2. **VN 是旗艦，短篇是主線**——龐貝當「第一個有美術的旗艦作」，其餘時代仍走純文字短篇。
3. ✅ **VN 就是短篇，只是加了美術**——維持 10–15 分鐘的內容單位與既有變現結構，但整條線都有背景與立繪。

> **✅ 已決（2026-08-13）：選 3**。（同日曾一度選 2，隨後撤銷。）
> **後果**：美術成本會傳染給每一篇，這個問題必須靠**資產結構**解掉而非靠規模——**背景庫以「景點」為攤提單位，一個景點包內 6–8 篇群像短篇共用同一套背景**。完整推導見 [[產品規格書]] §2，選點標準見 [[故事景點選點標準]]。

## L1 命題層——這故事憑什麼是這故事

四件產出物，加起來不超過一頁：

### 1. Logline（一句話）
`在 [時空]，[身分] 的 [主角] 必須 [目標]，否則 [代價]。`
一句話講不完，代表 L1 還沒想清楚，不要往下走。

### 2. 戲劇問題（Dramatic Question）
全篇要回答的那個問題。**龐貝題材的難點在這裡**：「城市會不會毀滅」不是問題，因為玩家一開始就知道答案。可用的問題形態有三種：

| 問題形態 | 例 | 張力來源 |
|---|---|---|
| **誰活下來** | 你救得了誰？救得了幾個？ | 資源／時間的取捨 |
| **代價是什麼** | 你為了活下來放棄了什麼？ | 道德成本 |
| **你成為誰** | 災難把你變成什麼樣的人？ | 角色轉變 |

三者可疊加，但**主軸只能有一個**——主軸決定結局矩陣的軸（見 L3）。

### 3. 能動性契約（Agency Contract）
明確寫下「玩家能改變什麼／不能改變什麼」，並且**在遊戲前 10 分鐘內就讓玩家感受到**。

歷史題材若不明講這件事，玩家會在結局處覺得被騙——「我做了那麼多選擇，結果城還是毀了」。反過來，若一開始就建立「你改變不了火山，你只能改變人」的契約，同一個結局會變成主題的實現而非背叛。

本專案的契約建議：**史實層不可改（火山必爆、城必毀），人物層完全可改（誰逃、誰留、誰記得誰）**——這條線恰好與 [[龐貝史實紅線]] 的三層分級同構，是很乾淨的設計。

### 4. POV 決策
| 選項 | 優點 | 成本 |
|---|---|---|
| 單一 POV | 敘事聚焦、資產量小 | 視野受限，難呈現全城 |
| 雙／三 POV 群像 | 能從不同階級看同一場災難（龐貝的階級落差就是題材本身） | 資產量與結構複雜度乘以 POV 數 |
| 可選 POV（開局選身分） | 高重玩價值 | 幾乎等於做 N 部作品 |

> 對一人團隊：**單一 POV 主線 ＋ 少數幾場切換視角的插敘**是成本／效果最佳解。

## L2 世界層——Setting Bible

VN 的世界層不只是背景設定，它是**寫作時的查詢表**。每次要寫一場戲時，需要能在 30 秒內查到「這個場合這個階級的人會怎麼稱呼對方／穿什麼／吃什麼／幾點在哪裡」。

### Bible 必備章節

| 章節 | 內容 | 龐貝的特殊注意 |
|---|---|---|
| **時空錨點** | 精確到日的時間軸 | 爆發日期本身有學界爭議，須選邊並記錄理由 |
| **史實紅線** | 不可動的記載事實 | → [[龐貝史實紅線]] |
| **真實度分級** | 史實 / 推定 / 虛構 三層標註 | 全篇每個斷言都要能歸到某一層 |
| **社會結構** | 階級、性別、贊助人—侍從關係 | 元老／騎士／自由民／被釋奴／奴隸的行為邊界差異極大，寫錯就穿幫 |
| **物質細節庫** | 食衣住行、貨幣、時制、度量 | 時代錯置陷阱清單見紅線文件 §4 |
| **語言風格指南** | 稱謂、命名法、禁用詞 | 羅馬命名法有硬規則，不能隨便取名 |
| **地理與場所** | 城內地標、動線、距離 | 直接對應 L5 的背景資產清單 |
| **來源清單** | 每個斷言的出處 | 有爭議者標記 ⚠ |

**寫 Bible 的原則**：只寫「會影響到某一場戲的內容」。世界觀寫到 5 萬字但一場戲都沒開始寫，是歷史題材創作最常見的死法。

## L3 結構層——分歧拓撲是成本的主控閥

### 3.1 分歧拓撲：四種選型

| 拓撲 | 形狀 | 內容量（相對主幹） | 適用 |
|---|---|---|---|
| **完全分歧樹** | 每個選擇都永久分開 | n 個二選一 → **2ⁿ 條路徑** | 幾乎不可行；5 個選擇就是 32 條結局 |
| **珠鏈式**（String of Pearls） | 分歧後立刻收束回主線 | 約 1.1–1.3× | 成本最低，但玩家易察覺選擇無效 |
| **分岔再收束**（Branch & Bottleneck） | 分歧展開數場後在關卡點收束，狀態被記住 | 約 1.3–1.8× | **一人團隊的最佳解** |
| **狀態驅動**（Stat-based） | 少數變數決定後續文本，分歧藏在數值裡 | 約 1.2–1.5× | ChoiceScript 主流做法，與既有產品規格相容 |

> **推薦：分岔再收束 ＋ 少量狀態變數**。玩家能感受到選擇有後果（因為狀態被記住並在後文回響），但寫作量不會指數爆炸。

### 3.2 狀態系統（旗標／數值）

**上限建議：3–5 個變數。** 每多一個變數，測試組合數就翻倍。

本題材適配的變數範例：
- `信任(某角色)`：0–100，決定災難時對方是否為你回頭
- `準備度`：前兩幕是否留意徵兆，決定第三幕可用選項
- `立場`：你在城裡站在哪一邊（影響誰願意幫你）
- `已知情報`：布林旗標集合（你知道什麼、不知道什麼）

**旗標表必須是一份獨立文件**，欄位：變數名、型別、值域、在哪些場設定、在哪些場讀取。缺這張表，測試階段必然出現「這個結局進不去」的死路。

### 3.3 結局矩陣

結局不是一個一個想出來的，是**由 2–3 個軸交叉而成的矩陣**。例：

|  | 你活下來 | 你沒活下來 |
|---|---|---|
| **他/她活下來** | 倖存者的餘生（史實上多數市民確實逃生成功） | 犧牲 |
| **他/她沒活下來** | 罪疚 | 一同埋葬 |

再乘上一個「你成為誰」的軸，就是 4–8 個結局——**這是一人團隊的合理上限**。每個結局都要能一句話講出它在回答 L1 的戲劇問題。

### 3.4 幕結構

災難敘事有天然的四段式，龐貝尤其乾淨：

| 幕 | 內容 | 玩家在做什麼 | 篇幅佔比（建議） |
|---|---|---|---|
| **I 日常** | 建立世界、人物、你在乎誰 | 認識人、建立關係值 | 30% |
| **II 徵兆** | 井水枯、地動、鳥獸異常 | 解讀線索、決定信不信 | 25% |
| **III 崩毀** | 浮石雨 → 火山碎屑流 | 高壓下的取捨 | 30% |
| **IV 餘生** | 倖存者去了哪裡 | 承受結果 | 15% |

**第 I 幕是最容易被寫壞的一幕**：因為玩家已經知道結局，日常戲若不承載「你在乎誰」的建立，就純粹是拖延。第 I 幕的每一場都必須至少完成一件事：**讓玩家在意某個之後會有生死風險的人**。

## L4 場面層——真正動筆前的最後一張表

### 4.1 場景清單（Scene List）

VN 製作的**核心工作文件**。一場一列，欄位：

| 欄位 | 說明 |
|---|---|
| `ID` | 如 `A2-03`（幕-序） |
| 地點 | 直接對應 L5 背景資產 |
| 時間 | 日／時（羅馬時制），決定背景時段變體 |
| 出場角色 | 直接對應 L5 立繪需求 |
| 劇情功能 | 一句話：這場戲改變了什麼 |
| 進入條件 | 需要哪些旗標 |
| 離場設定 | 設定哪些旗標 |
| 選項數 | 0／1／2… |
| 預估字數 | 用來估總量與進度 |
| 資產需求 | 新背景？新立繪表情？新 BGM？CG？ |

**這張表填完，才第一次知道這部作品到底多大、要多少美術、要做多久。** 在此之前所有的成本估算都是猜的。

### 4.2 角色卡

每個有名字的角色一張，欄位：**目標／恐懼／秘密／說話特徵／階級與其行為邊界／與其他角色的關係／在史實紅線中的層級（史實人物？虛構人物？）**。

最後一欄是本專案特有的：虛構角色與史實人物同框時，**虛構角色不得改變已知事件的結果**（詳見 [[龐貝史實紅線]] §3）。

### 4.3 劇本格式

**原則：寫作格式與引擎語法分離。** 用純文字（Markdown 或 ink）寫劇本，最後再轉成引擎腳本。理由：

- 純文字可版本控制、可 diff、可全文搜尋
- 換引擎時不必重寫
- 寫作時不被語法打斷

### 4.4 選項寫作規則

選項是 VN 唯一的互動介面，寫壞了整個結構層都白做：

1. **選項之間要有資訊差或價值差**，不能只是語氣差異
2. **不能有明顯正解**——一看就知道該選哪個，等於沒有選擇
3. **避免假選項**（選了但什麼都沒變），除非那是刻意的主題表達
4. **選項文字要是行動，不是感受**——「衝進屋內」優於「感到擔心」
5. **災難片的選項要有時間壓力感**，但慎用強制計時器（在文字介面容易變成焦慮而非張力）

## L5 呈現層——資產清單

### 5.1 數量估算公式

| 資產 | 公式 | 備註 |
|---|---|---|
| 背景 | 場所數 × 時段變體數 | 龐貝的時段變體特別重要：晴日／灰雨／夜／火光 |
| 立繪 | 角色數 × 表情數（3–8）× 服裝變體 | 表情數是成本乘數，先鎖上限 |
| 事件 CG | 關鍵場面數（含各結局） | 通常是單價最高的資產 |
| BGM | 情境數（日常／緊張／崩毀／餘韻／片尾） | 5–8 首可撐完一部中短篇 |
| 音效 | 環境音 ＋ 事件音 | 見下方「火山是時鐘」 |
| UI | 標題／選單／對話框／存讀檔／結局收藏 | 常被低估的一整包工作 |

> 各項的**單價**需另外查證（委外報價／素材庫／AI 生成的實際成本），本文件不臆造數字。這應該是繼此文件之後的一份獨立研究，與 [[敘事體驗產品價格研究報告]] 的成本面對接。

### 5.2 龐貝專屬的美術考據點

- **壁畫四風格**（First–Fourth Style）：房屋的壁畫風格能直接標示屋主階級與年代，是免費的視覺敘事
- **街道**：高起的人行道、過街墊腳石、車轍
- **公共空間**：Forum（62 年地震後仍在修復中的工地狀態）、劇場、浴場、麵包坊
- **災難各階段的天色**：這是本作最重要的視覺資產——白晝變黑、浮石堆積高度隨時間上升、最後的火山碎屑流
- **注意**：遺址現況的顏色 ≠ 西元 79 年的顏色。古城當年是彩色的、有屋頂的、吵鬧的

### 5.3 音效的敘事功能

災難敘事裡，**聲音就是時鐘**。浮石落在屋瓦上的密度、地鳴的頻率，可以在不寫一個字的情況下告訴玩家「時間不多了」。這是 VN 相對於純文字最大的優勢之一，值得在 L0 就把音效預算保住——**若要在美術與音效之間砍一項，砍美術的精細度、保音效**。

## L6 生產層

### 6.1 一人團隊 Pipeline

```
L0 規格書
  → L1 命題（1 頁）
  → L2 Bible（只寫會用到的）
  → L3 分歧拓撲 ＋ 旗標表 ＋ 結局矩陣
  → L4 場景清單（全作） → 角色卡 → 逐場寫劇本
  → L5 資產清單 → 委外／生成 → 引擎組裝
  → L6 Playtest → 修 → 上架
```

**唯一該打破這個順序的地方是「垂直切片」**（見 6.3）。

### 6.2 QA 檢查項（VN 特有）

- **分歧覆蓋率**：每條路徑至少被走過一次
- **不可達節點**：有沒有旗標條件永遠不成立的場
- **死路**：有沒有走進去出不來的狀態
- **旗標一致性**：先讀後寫的順序錯誤
- **回溯／跳過已讀**：功能壞掉會直接勸退重玩的玩家
- **存檔相容**：改劇本後舊存檔是否還能讀
- **史實回歸檢查**：每次改稿後，被動到的段落是否仍符合 [[龐貝史實紅線]]

### 6.3 垂直切片優先

**在寫完全作之前，先做完一章的完整成品**——含美術、音效、UI、可玩。

理由：
1. 這是**唯一**能算準「一章要花多久／多少錢」的方法，其餘都是估
2. 它同時是可拿去驗證市場的東西——與 [[營收天花板與地板估算報告]] 的結論一致（先在零成本通路驗證不是保守，是唯一理性）
3. 若切片做完覺得不對，損失是一章而不是一部

**切片規格建議**：第 I 幕的 15–20 分鐘、3 個有效選擇、2 個分支去向、完整美術與音效。
